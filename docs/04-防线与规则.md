# 04 · 防线与规则

## 1. 数据来源

| 来源 | 路径 | 解析器 | 说明 |
|---|---|---|---|
| 演示站访问 | `logs/app_access.jsonl` | `jsonl_http` | 含 `honeypot` 字段 |
| 演示站登录 | `logs/app_auth.jsonl` | `jsonl_auth` | 只记录结果，不记密码 |
| Suricata | `/var/log/suricata/eve.json` | `suricata_eve` | 只收 `event_type=alert` |
| ModSecurity | `/var/log/nginx/modsec_audit.json` | `modsec_json` | JSON 审计，4xx/5xx |
| nginx 限流 | `/var/log/nginx/nw_access.log` | `nginx_json` | 只收 429 |

> ModSecurity 审计日志故意用 `.json` 后缀，避开 nginx 包 `/var/log/nginx/*.log` 的 rename 轮转；
> 否则 ModSecurity 会一直写旧 `.1`，新文件永远为空。轮转使用 copytruncate。

## 2. 应用层规则

| rule_id | 条件 | 动作 | TTL |
|---|---|---|---|
| `BRUTE_FORCE.v1` | 60 秒内登录失败 ≥5，且窗口内无成功登录 | ban | 600s |
| `PATH_SCAN.v1` | 60 秒内 404 ≥8，且 ≥5 个不同敏感路径 | ban | 600s |
| `SUCCESS_IN_WINDOW` | 失败 <5 且有成功登录 | observe | — |
| `SUCCESS_AFTER_THRESHOLD` | 失败 ≥5 后出现成功登录 | alert | — |
| `BELOW_THRESHOLD` | 失败 ≥3 但 <5，无成功 | observe | — |
| `WHITELIST` | 来源命中白名单 | no_action | — |

敏感路径前缀：`.env`、`.git/config`、`wp-login.php`、`phpmyadmin`、`admin.php`、`.aws`、`backup`、`actuator`、`console`、`config.json`。

## 3. 网络层（Suricata）

Suricata 使用 **pcap** 同时监控 `wlp1s0` 与 `nw-kali0`（无线网卡 AF_PACKET ring 不可用）。
只输出 `event_type=alert`。

| 匹配（category/签名） | rule_id | 阈值 | TTL | 自动封 |
|---|---|---|---|---|
| ET SCAN / Nmap / Nikto / scanner | `NET_SCAN.v1` | 60s ≥3 条 | 1800s | 是 |
| ET DOS / flood / denial of service | `NET_DOS.v1` | 规则自身已限阈值；命中即处置 | 600s | 是 |
| ET EXPLOIT / Web Application Attack | `NET_EXPLOIT.v1` | 单条 | 3600s | 是 |
| ET TROJAN / MALWARE / CINS | `NET_C2.v1` | 单条 | 3600s | 是 |
| ET POLICY / INFO / 未匹配 | `NET_ALERT.v1` | 仅记录 | — | 否 |

本地兜底规则（`deploy/suricata/local.rules`）：

```text
NW SCAN SYN burst >=50/10s    -> NET_SCAN
NW SYN FLOOD 8081 >=200/10s   -> NET_DOS
NW LAB INFO probe             -> NET_ALERT（给 AI 演示低置信告警）
```

## 4. Web 层（ModSecurity CRS）

`nginx :8081` 反向代理到演示站 `127.0.0.1:8082`。
`SecRuleEngine On`，CRS 3.3.5，PL1，入站阈值 5。

| CRS 段 | rule_id | TTL | 自动封 |
|---|---|---|---|
| 913 扫描器 | `WAF_SCANNER.v1` | 3600s | 是 |
| 930/931 LFI/RFI | `WAF_LFI.v1` | 3600s | 是 |
| 932/933/934/944 RCE/注入 | `WAF_RCE.v1` | 3600s | 是 |
| 941 XSS | `WAF_XSS.v1` | 1800s | 是 |
| 942 SQLi | `WAF_SQLI.v1` | 3600s | 是 |
| 920/921 协议异常 | `WAF_PROTOCOL.v1` | — | 仅告警 |
| 949 入站阈值 | 继承明细；无明细 `WAF_BLOCK.v1` | 600s | 是 |
| 其它 | `WAF_ALERT.v1` | — | 否 |

nginx 限流：

```nginx
limit_req_zone $binary_remote_addr zone=nw_req:10m rate=20r/s;
limit_req zone=nw_req burst=40 nodelay;
limit_req_status 429;
```

60 秒内 ≥60 个 429（或总请求 ≥600）→ `HTTP_FLOOD.v1`，TTL 300s。

## 5. 主机层（nftables）

专用表：

```nft
table inet nightwatch {
  set nw_block { type ipv4_addr; flags timeout; size 65536; }
  set nw_allow { type ipv4_addr; flags interval; elements = { ... }; }
  chain input {
    type filter hook input priority -10; policy accept;
    ct state established,related accept
    ip saddr @nw_allow accept
    tcp dport 22 accept
    ip saddr @nw_block drop
  }
}
```

- **没有 policy drop**，未命中流量自然放行。
- 22 端口在 block 之前 accept，**永远不封 SSH**。
- `nw_allow` 是 root 维护的 `/etc/nightwatch/fw-allow`；应用配置白名单只用于应用层。
- li 只能通过 `/usr/local/sbin/nw-fw` 操作；wrapper 校验 IP/TTL/白名单，拒绝环回/保留/组播。
- 封禁默认 600 秒；nft set 元素自带 timeout，到期内核自动删除；应用 sweep 再记账。

## 6. 蜜罐

演示站：

| 路径 | 返回 | 事件 |
|---|---|---|
| `/admin` | 假后台登录页 200 | `honeypot=admin` |
| `/.env` | 假配置（假 AWS Key）200 | `honeypot=env` |
| `/wp-login.php` | 假 WordPress 登录页 200 | `honeypot=wordpress` |

正常用户不会访问；命中即 `HONEYPOT.v1` 封 3600 秒，零误报。

## 7. 动态 WAF 规则

AI 通过 `deploy_waf_rule` → root wrapper `nw-waf`：

- 模板：`UA @contains` 或 `REQUEST_URI @beginsWith`
- 值只允许 `[A-Za-z0-9._:/%+-]{2,64}`
- 最多 3 条
- 追加到 `/etc/nginx/modsec/ai-rules.conf`
- `nginx -t` 失败自动回滚
- `restart nginx` 生效（`reload` 不会重载 ModSecurity 规则）

## 8. 负证据

所有“没封”的判断都写 `decision / observe`：

- `WHITELIST`
- `ALREADY_BANNED`
- `SUCCESS_IN_WINDOW`
- `BELOW_THRESHOLD`
- `UNTRUSTED_CLIENT_IP`
- `AUTO_DISABLED`

这是“为什么没封”的可审计依据。

# 02 · 架构设计

## 1. 总览

```text
攻击者（Kali / netns）
        │
        ▼
Suricata（pcap: wlp1s0 + nw-kali0）──► eve.json
nginx :8081 + ModSecurity/CRS ──► modsec_audit.json / nw_access.log
演示站 :8082 ──► app_access.jsonl / app_auth.jsonl
        │
        ▼
TailSource × N ──► queue ──► 单写线程
                              │
                              ├─ Detector（滑窗）
                              ├─ decide()（纯函数）
                              ├─ Enforcer（应用层 403 + nftables）
                              ├─ Store（SQLite 哈希链）
                              └─ CLI / watch / battle TUI
```

## 2. 进程/线程

`nightwatch daemon` 一个进程内：

| 线程 | 作用 |
|---|---|
| TailSource ×N | 每个日志源一个 `tail -F -n 0` 子进程，逐行投递 `(source, parser, line, path, offset)` |
| writer | 唯一写 SQLite 的线程；解析、检测、裁决、封禁、入链都在这里串行 |
| sweeper | 每秒检查封禁到期，写 `expire` 事件并删除 nft 元素 |
| autopilot | 每 30 秒检查新告警，有新告警才调模型；否则不调用 |
| TUI/CLI | 独立进程或线程，只读 SQLite；TUI 的 BattleAgent 可执行封禁 |

单写线程的意义：

1. 事件 id 顺序 = 提交顺序，SSE/终端看到的就是落库顺序；
2. 不需要跨线程事务协调；
3. 所有处置都在一个地方发生，便于审计。

## 3. 事件流

统一事件结构 `ParsedEvent`：

```python
ts, ip, kind, user, path, status, ua, raw_line,
source_file, source_offset, extra
```

`kind` 取值：

- 应用层：`login_fail` / `login_success` / `http_404` / `http_request` / `http_429`
- 网络层：`net_alert`
- Web 层：`waf_alert`
- 蜜罐：`honeypot`
- 裁决：`decision` / `rollback` / `firewall`
- Agent：`agent_tool` / `agent_run` / `agent_autonomy`
- 异常：`parse_error` / `enforce_error`

原始事件与裁决事件都写入同一账本。

## 4. SQLite 表

```sql
meta(k TEXT PRIMARY KEY, v TEXT)
events(
  id INTEGER PRIMARY KEY,
  ts TEXT, kind TEXT, ip TEXT, rule_id TEXT,
  evidence_json TEXT, raw_line TEXT,
  source_file TEXT, source_offset INTEGER,
  canonical TEXT, prev_hash TEXT, hash TEXT
)
bans(ip TEXT PRIMARY KEY, until_ts TEXT, decision_event INTEGER,
     created_ts TEXT, revoked_ts TEXT, operator TEXT, reason TEXT)
audit_runs(id INTEGER PRIMARY KEY, ts TEXT, project TEXT,
           snapshot_ts TEXT, source TEXT, summary_json TEXT)
findings(id INTEGER PRIMARY KEY, run_id INTEGER, group_key TEXT,
         pkg TEXT, version TEXT, cve TEXT, scope TEXT,
         verdict TEXT, reason_code TEXT, evidence_json TEXT)
```

WAL + `busy_timeout=3000`；CLI/TUI 只读连接，daemon 单写连接。

## 5. 哈希链

写入时：

1. 在 `BEGIN IMMEDIATE` 事务内读取 `meta.event_count` / `meta.last_hash`；
2. `id = count + 1`；
3. 组装 `canonical` JSON（`sort_keys=True`、无空格、UTF-8）；
4. `hash = sha256(prev_hash + "\n" + canonical)`；
5. 插入 events，同时更新 `meta.event_count` / `meta.last_hash`；
6. 提交。

校验时：

- `meta.event_count` 必须等于实际行数；
- id 必须从 1 连续；
- 每行 `prev_hash` 必须等于上一行 hash；
- 重算 canonical 的 sha256 必须等于行 hash；
- 行的 ts/kind/ip/rule/evidence/raw/source 必须与 canonical 内字段一致；
- 最后一行 hash 必须等于 `meta.last_hash`。

因此：改中间行、改列内容、删尾部都能发现。
注意：哈希链是 tamper-evident，不是 tamper-proof；有 DB 写权限的人可以整库重写，需要外部锚点/备份。

## 6. 检测

每 IP 维护 1 秒桶（默认窗口 60 秒），桶内累计：

- `f` 登录失败、`s` 登录成功、`p404` 404 数、`paths` 敏感路径集合
- `ids` 网络告警、`waf` WAF 告警、`req`/`r429` HTTP 请求与限流
- `hp` 蜜罐命中、`id_counts` / `waf_counts` 规则计数

规则见 [04-防线与规则](04-防线与规则.md)。`_emit` 用 `(ip, rule)` 做冷却，避免同一攻击刷屏。

## 7. 裁决

`app/decide.py:decide(sig, cfg, now, whitelisted, already_banned, auto_enabled)` 是纯函数，顺序：

```
AUTO_DISABLED → WHITELIST → ALREADY_BANNED
→ NET_/WAF_/HTTP_FLOOD/HONEYPOT
→ PATH_SCAN → SUCCESS_IN_WINDOW/SUCCESS_AFTER_THRESHOLD
→ BRUTE_FORCE → BELOW_THRESHOLD
```

不封也写一条 `decision / observe` 事件（负证据），例如：

- `WHITELIST`：命中白名单
- `SUCCESS_IN_WINDOW`：失败少且有成功登录
- `BELOW_THRESHOLD`：失败次数没到阈值
- `ALREADY_BANNED`：已封禁

## 8. 处置

`Enforcer.handle`：

1. 写 `decision` 事件；
2. 若 action=ban：写 `bans` 表，调用 `app/fw.py` → `sudo nw-fw ban` → nftables set；
3. 发布（daemon 没有 SSE；CLI/TUI 读 DB）；
4. 失败写 `enforce_error`，应用层 403 兜底。

到期：sweeper 删除 nft 元素并写 `expire`。
回滚：`unban` 写 `rollback` 事件、删 nft 元素。
启动：`enforcer.reconcile()` 按账本回放 nft 集合。

## 9. 应用层封禁

演示站中间件在每次请求前查 `bans` 表：命中返回 403 并记录访问。
两层都保留：

- 正常情况下 nftables 先丢包，攻击者看到连接超时；
- nft 后端失败时，应用层 403 仍然生效；
- 127.x 回环来源由应用层兜底，nft 跳过（`FwBackend` 对 loopback 返回 skipped）。
